# 人生重开 · 修仙（byxz）

小米手环（Vela 快应用）上的**人生重开模拟器**：抽天赋词条 → 分配属性 → 逐年推进人生 →
踏上**修仙 / 炼体 / 魔法 / 科技**四条体系之一（境界 / 突破 / 劫难）→ 死亡结算评分 → 词条图鉴收集。

- 产物：`dist/人生重开修仙_byxz.bin`（约 211 KB）
- 包名：`com.byxz.liferestart`，版本 2.2.0
- 参考原作：`人生重开模拟器`（`com.application.watch.liferestart`）——那是一份 87 条线性事件、
  4 属性、无天赋抽取、无修仙的简版。本作在同样的骨架上做了**大幅扩充**。

## 0. v2.2 修复：手环上"几乎每局都重启"

四个原因，都在**内存与渲染量**上（本作没有棋类那种长计算，`step()` 一年只扫一遍 1065 条事件表）：

| 问题 | 原来 | 现在 |
|---|---|---|
| **页面栈泄漏**：抽词条→分配→人生→结算一路 `router.push`，退回首页的旧页仍留在栈里，每页一个 VM | 玩 N 局攒约 2N 个页 | 推进全用 `replace`，栈恒定 1 页 |
| 内容被 6 个页面各自 `import`：每页 `.jsc` 内联一份完整内容，换页反复解析构造约 1.5 MB 对象 | 每页 317 KB | 每页 30 KB |
| 图鉴一次把 649 条全渲染（约 1900 个原生控件），同步渲染过长触发看门狗 | 一次 649 行 | 40 行/页，带翻页 |
| 修仙顶阶能活数千岁，日志无上限（实测一局 2292 条、存档 191 KB） | 2292 条 | 封顶 300 条（存档 31 KB） |

前两条叠加最致命：旧页留在页面栈里 × 每页一份 1.5 MB 内容 → 玩三局就吃掉近 5 MB，手环直接重启。

做法：① 只有"进入下一阶段"的跳转改成 `replace`（抽词条→分配→人生→结算，以及结算的"再来"），
图鉴/设置这类可返回的仍用 `push`；分配页的"返回"改成显式回首页（栈里已没有可回退的页）。
② 内容只在 `app.ux` 装配一次（`content/index.js` 的 `buildContent()`），页面通过
`this.$app.$def.CONTENT` 拿**同一份引用**交给 `engine.setContent()`，全应用内存里只有一份内容，
页面字节码里也不再重复打包。③ 日志每条带一个只增不减的 `seq` 当界面行 id，封顶丢旧条目时
已有行不会整体错位、不必整屏重建。顺带修掉"死亡后 0.7 秒延时跳转撞上手动结束"的重复跳页。

结果：`.bin` 746 KB → **211 KB**，`.jsc` 总量 1.9 MB → 474 KB，内容对象从"每页一份"变成全应用一份。
新增回归测试：日志条数 ≤ 300、`seq` 严格递增、单局存档 < 120 KB。

**v2.2.1**：结算页那 7 张信息卡原来是 `width: 84px` + 3px 边距（两张 180px），
装不进 176px 的可用宽度（212 − 左右各 18），设备上被挤成"一行一张"并整体横向错位。
改成 80px（两张 172px，与主菜单同一套已验证配置）就居中了，页面也因此矮了约 200px，
底部「重开人生」按钮回到屏内——和当初主菜单"塌成一列"是同一个坑，结算页漏改了。

另有「**双修**」天赋可以再开一条体系（两条同时增长，有专属跨界事件与结局）。

## 2. 玩法

1. **抽天赋**：每局随机给 10 个词条，选 3 个带走（可换一批）
2. **分配属性**：20 点分配到 智力 / 情商 / 体质 / 幸运——属性决定你能遇到什么事
3. **推进人生**：手动「下一年」或开「自动」快速播放；每年一个事件
4. **踏入体系**：靠天赋自带（灵根 / 体魄天赋 / 魔力天赋 / 科研天赋），或碰上机缘
   （**机缘带幸运门槛，所以属性分配要真正想清楚**）。四个体系只能选一条，抽到双修天赋才能走两条
5. **修炼**：资源积累满自动尝试突破，突破**消耗资源**、失败受伤并掉特殊属性；劫难有生死判定。
   境界越高寿元越长，但顶级境界极难（仙人约 2%）
6. **结算**：按享年 / 体系 / 境界 / 评分给评级与结局，达成的成就与遇到的词条进图鉴
7. **图鉴**：**体系 / 天赋 / 物品 / 结局 / 成就** 五类，反复游玩逐步解锁（存档持久化）

### 平衡（`node tools/balance.mjs 400` 实测，v2.1）

| 指标 | 数值 |
|---|---|
| 享年 | 中位数 **75 岁**，平均 148 岁 |
| 入体系率 | **34.5%**（其余为凡人一生）；四条体系都有：修仙 65 / 炼体 30 / 魔法 25 / 科技 18（每 400 局） |
| 境界分布 | 多数止步炼气/筑基、淬筋/易骨、中级法师、工程师一级；顶级（仙人/法神/肉身成圣/机械飞升）合计约 2~4% |
| 死因 | 体魄衰败 41% / 寿终正寝 30% / 意外 17% / 寿元耗尽 5% |
| 结局 | 游戏里的NPC 19% / 名留青史 18% / 平凡一生 17% / 小康之家 14% / 家庭美满 5% |

标定过程中发现并修掉的三个问题（都是"跑数据"才暴露的）：

1. **突破不消耗资源** → 攒一次就连跳到底，300 局里修仙者几乎人人成仙。改成突破扣掉该境界门槛后正常
2. **新体系阶梯太便宜** → 炼体总门槛只有修仙的 1/27，实测 `肉身成圣 97 局 / 法神 52 局`（满地顶级）。
   按修仙的经济重新标定（门槛 18~19 万、寿命 3~5 千年）后，顶级境界降到 2~4%
3. **入门太容易** → 四体系共 36 条入门事件 + 词条，实测 95% 的人都能修炼。
   给入门事件加**幸运门槛**（炼体/魔法/科技 ≥6、修仙 ≥7）、权重压到 1，体系词条降为灵品后降到 32.5%

另外还修了两个工程问题：**事件 `once` 默认必须是 true**（否则「一场大病」连着 4 年触发，7 岁就死）、
**体质要有恢复 + 大难不死**（否则 85% 死于"体魄衰败"、平均只活 36 岁）。

## 4. 构建与自检

```bash
npm install
bash tools/build-bin.sh      # 内容校验 → 内核测试 → 页面检查 → 编译 → 出 .bin
```

单独使用：

```bash
node tools/validate-content.mjs    # 内容结构校验（改内容后必跑）
bash tools/run-tests.sh            # 内核测试（17 项：分配/事件/四体系/复现/序列化/日志封顶/200 局不崩）
node tools/balance.mjs 300         # 平衡统计
node tools/preview.mjs && bash tools/preview.sh   # 渲染成 212×520 截图（目视检查）
```

调试与安装同《棋类博弈》：`printf 'y\ny\ny\n' | npx aiot start` 装到模拟器，
`node tools/emulator-shot.cjs <虚拟机名> shot.png` 截图（模拟器搭法见棋类博弈仓库的 `docs/模拟器.md`）。

## 5. 已知取舍

- **属性波动**：事件大多带属性增减，一生会漂移十几点，所以初始分配的影响是"倾向"而非"定死"
- **凡人结局偏多**：41% 是「平凡一生」，因为结局门槛用的是 20 点总量下的属性，高门槛结局较难达成
  （这也是本作想表达的：大多数人就是平凡一生）
- **自动播放**：默认 420ms 一年；设置页可切「快速」（该开关目前只存偏好，未接速度）
- 无存档续玩界面：一局中途退出会丢，图鉴会保留
- **包体与内存（v2.2 已修）**：工具链按页面打包，页面各自 `import` 内容会把完整内容内联进每页的
  `.jsc`，换页时反复解析构造约 1.5 MB 对象，手环内存耗光就重启。现在内容只由 `app.ux` 装配一次，
  页面注入同一份引用（见第 0 节）。当前：`app.jsc` 300 KB（唯一一份内容）+ 每页约 30 KB。
- 未在真机验证（模拟器那份"不带表盘"镜像没有合成器，截图是黑的；界面靠 `tools/preview/out/*.png` 目视把关）
